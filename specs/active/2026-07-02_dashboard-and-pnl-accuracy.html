Two facts that shrink this whole effort:
  • A full dashboard already exists and is deployed — options_owl/dashboard/, the owlet-dashboard service on port 8443. It already has bcrypt+JWT login, per-owlet isolation (each user sees only their agent via an agent_id-scoped query), a live WebSocket feed, and analytics pages. We extend it — we do not build a new one.
  • Webull already exposes ground truth — order_v2.get_order_history() returns the broker's own settled fills + quantities per order, immune to the intraday rate-limit races that corrupt our live numbers. Reconciling against it is fully out-of-band (zero trading risk).
The #1 rule for every item below. Nothing in this spec may add a blocking call, a lock, or a failure mode to the ~5 s position-monitor loop or the order-placement path. Monitoring is read-only; new data capture is fire-and-forget to a separate sink; P&L correction happens out-of-band against Webull's own history. If any single change here carried a non-trivial chance of stopping a bot from selling, it is deferred or redesigned.

Executive summary

You currently cannot trust the recorded P&L: for adam today the DB showed +$538 while the brokerage finished −$125.16. This is not one bug — it's five compounding ones on the trade-close path (below), and it poisons everything downstream, including the dashboard, which reads the same numbers from Postgres. Workstream A fixes the numbers; Workstream B is worthless until A is done.

  • A — P&L accuracy (foundation, do first). Make Webull's own order history the source of truth.   • B — Dashboard verbosity (build on what ships). Reuse the existing auth + per-owlet isolation + WebSocket. Add the verbose per-trade lifecycle timeline vinny wants — powered by piggybacking the FSM's already-computed per-cycle state onto the existing fire-and-forget 15 s premium-tick flush, so it adds zero latency to the exit path.

What: After close each day, pull executor.get_order_history(start, end) per bot — Webull's own settled fills + quantities (+ fees). Group orders into trade families by (day, symbol, strike, expiry, type), handling DCA adds and scale-out children. Compute realized P&L per family = Σ sell_proceeds − Σ buy_cost − fees. Then write the truth back:

  • webull_entry_fill_price / webull_exit_fill_price (columns already exist), exit_premium and pnl_dollars — including exit_premium, which no current script fixes.
  • Correct paper_portfolio.current_balance / daily_pnl / wins / losses — which no current script does. This is the missing piece that lets the recorded balance match the brokerage.
  • Mirror all corrections into Postgres (trades, agent_state) so the dashboard and trade-pnl.py both inherit the truth.
Why zero-risk It runs as a standalone script/cron (or a job in the owlet-dashboard container), out-of-band, after market close. It only reads Webull and corrects historical rows — it never touches the live monitor loop, the order path, or an open position. Ships with a report-only mode (default) that prints "Webull says $X, DB says $Y, diff $Z per trade" and writes nothing until --fix.

Acceptance: run it for adam today → the reconciled total equals the brokerage's −$125.16, with a per-trade diff table showing exactly where the DB was wrong (expect: the MU stale-fill + missing fees + 429-missed fills).

The good news: the FSM already computes the entire rich per-cycle state every ~5 s — state (GRACE/DEVELOPING/TRAILING), gain_pct, peak_gain_pct, drop_from_peak, active stop, underlying_move, which gate would fire — in the evaluate() debug dict. The safe way: the monitor already buffers a trade_premium_ticks row every 15 s and flushes it fire-and-forget to Postgres. Piggyback the FSM debug snapshot onto that same throttled, non-blocking flush — either as JSONB columns on the tick, or a sibling trade_state_snapshots table written by the same buffer. Zero added latency on the exit path, zero change to exit logic — we serialize a dict that already exists in memory.

Safety architecture & non-goals (applies to everything)

  • Read-only to trading. The dashboard never writes a trading DB. Reads target Postgres (the shared store) or read-only SQLite (mode=ro), never contending with the bots' WAL writers.
  • Physically separate process. All UI/serving stays in the owlet-dashboard container (already memory-capped, own port). A crash/OOM there cannot touch a bot.
  • New capture is fire-and-forget to a separate sink. No new await DB write inside FSM evaluate() or the gate critical section — reuse the existing throttled, non-blocking premium-tick flush.
  • Monitor-only in v1. You said both "manage their bots" and "zero chance to break things, just monitor." We honor the second: v1 is read-only. The existing kill-switch/paper-mode controls stay as they are (no new control actions, no per-owlet self-serve kill of a live bot) until a separately-specced, audited Phase 2.
