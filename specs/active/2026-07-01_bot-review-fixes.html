Critical & high bugs

B1V6 DCA Webull calls freeze the monitor loopbugcritical
options_owl/execution/position_monitor.py:506 & :518 (_check_v6_dca, called from the 5s loop at :1528, gated at :1523)

What’s wrong. await webull_executor.buy_option(...) and await webull_executor.get_fill_price(...) are not wrapped in asyncio.wait_for. The surrounding try/except catches exceptions but not a hang. The sibling sell path deliberately wraps its Webull call in asyncio.wait_for(..., timeout=45) (paper_trader.py:2191) with a comment that a hung SDK socket must not stall the loop — the DCA buy path violates that same rule.

Live? (droplet-verified via SSH). Yes. ENABLE_V6_DCA=true in the running containers of all four live bots (kody/adam/dennis/vinny) + yank. The guard at position_monitor.py:1523 genuinely gates the call, and the deployed source at :506/:518 has the unguarded awaits (every other loop I/O uses wait_for). Prod logs show the path has actually fired (V6 DCA Webull FILLED ×2). Scoped to V6_DCA_TICKERS=IWM,SPY,QQQ,AMZN,NVDA, dip 15–35%.

Failure scenario. An SPY position dips 20% → DCA fires → the Webull SDK socket is in the documented “no active connection” stale state → the buy_option await never returns → the entire monitor loop freezes → no other open position can be evaluated or sold. This is the exact unlimited-loss freeze class the safety rules exist to prevent.

Proposed fix. Wrap both awaits in asyncio.wait_for(..., timeout=15) (buy) / timeout=10 (fill lookup) with graceful fallback (log + skip the add, keep the parent). Apply the identical guard to _check_antimartingale_add (:709,:719) so the latent path is safe too.

Confidence: High (code); DCA is live but ticker-scoped, so freeze odds are moderate, impact catastrophic.

B2V6-DCA’d trades reconcile against the wrong entry basis → wrong P&Lrefuted
paper_trader.py:1607 (open) & :2291–2294 (reconcile) — verified on the droplet source

Original claim. That _check_v6_dca never sets dca_total_contracts, so the exit reconcile falls back to the raw first-leg fill and mis-computes P&L on DCA’d trades.

Why it’s refuted (SSH-checked). dca_total_contracts is set to the initial contract count at open for every trade (paper_trader.py:1607, unconditional) — droplet data confirms 371 of 427 kody trades have it >0. The reconcile only uses it as a boolean gate (dca_qty > 0) and then reads premium_per_contract as the entry basis — which _check_v6_dca does correctly update to the blended average. The exact value of dca_total_contracts never feeds the P&L math; the only place it’s used as a quantity is the separate V3 dca_add_contracts path (:3534), which V6 DCA doesn’t touch. So V6-DCA’d trades reconcile on the correct blended cost. No fix needed.

Status: Refuted during droplet verification. Retained here for the audit trail.

B3Entry re-anchor backstop can corrupt a correct fill basis on a real fast 0DTE move✅ fixed + deployed

Resolution (2026-07-02, commit ddd817b). Found firing live — worse than the spec first described. The real culprit: _reconcile_entry_to_fill (which anchors the FSM to the real Webull fill) bailed on dca_total_contracts > 0, which is true on every trade (it's the initial contract count, not a DCA marker), so the reconcile never ran — the FSM stayed on a phantom basis. Fixed by (1) detecting a real DCA the way _build_state does (add-marker or blended-vs-fill divergence), so reconcile anchors normal trades to the actual fill, and (2) a new entry_from_real_fill flag so the live-premium fallback can never override an authoritative basis. Verified live on adam MU #399 (phantom $3.82 → stopgap $9.78 → real fill $11.54). Full suite 2737 passed.

options_owl/risk/exit_v5/monitor_bridge.py:299–318 (evaluate-time fallback)

What’s wrong. The one-shot fallback re-anchors entry_premium = exit_premium whenever |(exit−entry)/entry| ≥ 0.70 within 60s of entry. It runs independently of the primary fill-reconcile (_reconcile_entry_to_fill), and its guard cannot distinguish a phantom pre-fill quote from a real ±70% 0DTE move. The comment’s claim that “>70% never clobbers a real gamma move” is false for 0DTE.

Failure scenario (loser hidden). Live fill correctly recorded at $1.00; underlying gaps against; first monitored cycle sees $0.30 (−70%). Backstop re-anchors entry → $0.30, but peak_premium stays $1.00 → computed peak_gain = +233%, gain = 0%. The real −70% loss is hidden and the profit-lock/hard-stop math is corrupted for the rest of the trade.

Failure scenario (winner clipped). A legit +70% ripper in the first 60s resets gain to 0, destroying the trail/profit-lock anchor — the winner must re-run to +70% before any lock re-arms.

Proposed fix. Gate the fallback so it only fires when there is no valid webull_entry_fill_price (i.e. paper / missing-fill only) — the live-fill case is already handled correctly by _reconcile_entry_to_fill. Equivalently: skip the fallback when the primary reconcile has confirmed the basis against a real fill.

Confidence: High on the code path; Medium on frequency (first cycle is usually ~5s post-fill, so most real moves aren’t yet 70% — but 0DTE gaps can be).

Medium bugs & risk-control correctness

B4_reconnect() leaves a stale market-data clientbugmedium
webull_executor.py:112–117 (_reconnect) + 1432–1441 (_ensure_data_client)

What’s wrong. _reconnect() nulls _api_client and _trade_client but not _data_client, and _ensure_data_client() early-returns when _data_client is not None. After any reconnect, the data client keeps wrapping the torn-down api client.

Failure scenario. After an idle-period stale-connection reconnect, _fetch_ask’s HTTP fallback uses the dead data client and fails silently → the entry chase falls back to the back-derived base_ask instead of a fresh quote — reintroducing the exact stale-limit “not filled” misses the 2026-06-25 live-quote fix was built to eliminate. Order placement still works (_trade_client), so it’s silent degradation, not an outage.

Proposed fix. Add self._data_client = None to _reconnect().

Confidence: High that state is lost; Medium on fill-quality impact.

B5_fetch_ask freshness guard bypassed when timestamp missingbugmedium
webull_executor.py:1124

What’s wrong. if ask > 0 and (ts <= 0 or time.time() - ts <= max_age): return ask — the ts <= 0 branch returns the Redis ask even when its age can’t be verified, defeating the docstring’s “a stale snapshot can never make the limit worse” guarantee. Also assumes t is epoch seconds; if the harvester ever writes milliseconds, time.time() - ts is hugely negative and always passes the guard.

Failure scenario. A snapshot missing its t field (→ ts=0) prices the chase off an arbitrarily old ask → un-marketable limit (miss) or over-aggressive within the ceiling.

Proposed fix. Treat ts <= 0 as stale (fall through to HTTP), not fresh. Confirm the harvester writes t in seconds; if ms, normalize.

Confidence: High on the ts<=0 fallthrough; Medium on the unit concern (depends on harvester write format — worth a quick check).

B6Daily loss-cap sums raw pnl_dollars → double-counts scaleout childrenbugmedium
position_monitor.py:1673–1680

What’s wrong. The max-loss circuit breaker does SUM(pnl_dollars) WHERE status='closed' AND webull_order_id IS NOT NULL. Scaleout/partial closes create a child row that copies the parent’s webull_order_id and carries its own pnl_dollars; the parent later closes with its own P&L on the remaining contracts. This is the exact double-count CLAUDE.md warns against (“Do NOT use SUM(pnl_dollars) directly”).

Failure scenario. On a multi-scaleout day the realized total is distorted → the loss-cap force-exit can trigger early on a green day or fail to trigger when it should. It’s a risk control fed by a known-unreliable aggregate.

Proposed fix. Compute the day’s realized P&L with the same family-grouping logic as scripts/trade-pnl.py (exclude child rows or group parent+children), or filter to parent rows only.

Confidence: Medium.

B7PutMarketDirectionGate fails closed on missing SPY change → whole PUT book blocked silentlybugmedium
pipeline.py:297–301

What’s wrong. If spy_change_from_open is None, every non-flow PUT is rejected. It’s a deliberate safety default, but a single unpopulated ctx key silently kills the entire PUT book with only per-signal log lines and no aggregate alarm.

Failure scenario. A regime/SPY-fetch failure leaves the key None during market hours → all ML/Discord puts rejected fleet-wide, unnoticed until someone reads logs.

Proposed fix. Keep fail-closed, but add a loud health signal: if the key is None for >N consecutive signals during market hours, fire a Discord alert (reuse the premium-failure alerter). Consider a one-shot HTTP SPY fallback before failing.

Confidence: Medium. Behavior is intentional; the gap is observability.

Profitability leaks

P1ML CALLs rejected in the prime 9:30–9:45 window (85-score threshold, no ML branch)profithigh
pipeline.py:1573 (early check) & :1587 (late check)

What’s wrong. The early (<9:45) and late (≥14:00) score checks compare signal.score to TOD_EARLY_MIN_SCORE / TOD_LATE_MIN_SCORE (default 85, not overridden) with no _is_ml_sourced branch. But AntiChaseGate (:1382) and PremiumCapGate (:683) both explicitly carry that branch, with a comment that ML scores (conf×100, capped 100) shouldn’t be rescaled onto the Discord range. TimeOfDayGate was missed.

Failure scenario. Verified: ML CALL score = int(pattern_conf×100); with the live ML_PATTERN_THRESHOLD=0.62 a passing call can score 62–84. Any such call firing before 9:45 ET → score < 85 → rejected, inside the backtested prime CALL window (9:30–10:30 = +$62k in the harness). The early check also hits ML puts (not put-exempt) with score 78–84.

Proposed fix (validate first). Add the same _is_ml_sourced handling used in AntiChase/PremiumCap — either exempt ML from the 85 gate or apply an ML-scaled early threshold (e.g. current pattern threshold). Backtest the change before shipping: the open-noise filter may be partly intentional, so confirm the morning window nets positive with ML included.

Confidence: High the mismatch exists and clips volume; the size of the gain needs a backtest.

P2Flow whale sweeps killed by the momentum/anti-chase gatesprofitmedium
pipeline.py:1400–1491 (MomentumConfirmGate), :1360–1397 (AntiChaseGate)

What’s wrong. Neither gate calls _is_flow_sourced. Flow explicitly bypasses the sibling directional gates (directional_regime, put_bearish_confirm, put_market_direction, put_ticker_exclusion) because “the whale IS the conviction,” yet momentum_confirm — functionally the same kind of directional-quality gate — still applies.

Failure scenario. A $6M ask-side SPY call sweep at 10:15 with the last three 5m candles red + soft RSI → MomentumConfirmGate collects 2+ negatives → FAIL, dropping a high-conviction entry. Same risk on AntiChaseGate if the underlying drifted >0.3% from the signal’s entry_price before processing.

Proposed fix (validate first). Add the _is_flow_sourced bypass to both gates for consistency with the documented flow-bypass set. Confirm on the flow gold-standard report that removing these two gates for flow doesn’t regress PF.

Confidence: Medium.

P3scalp_trail dumps a 0DTE runner when underlying data is merely missingprofitmedium
gates.py:117–123 + fsm.py:587–589

What’s wrong. _compute_underlying_move returns underlying_confirms=False when there’s no underlying price (has_underlying=False). The 0DTE branch of check_scalp_trail exits on not underlying_confirms — so missing data is treated as disconfirmation on the exit-a-winner path.

Failure scenario. A 0DTE call peaks +30%, fades to +17% (<60% of peak), and the underlying feed has a transient gap that cycle → underlying_confirms=False → scalp-trail exits a genuine runner purely because underlying data was absent.

Proposed fix. Distinguish “underlying against” from “no underlying data.” When has_underlying=False, HOLD (let the adaptive/soft trail handle it) rather than treating absence as disconfirmation.

Confidence: Medium.
